# Бэкенд «Спорт и точка»: архитектура и запуск

Сервер исполняет контракт HTTP API (`docs/architecture/api.md`): ресурсы, действия, права, переходы статусов, тексты уведомлений и коды ошибок. Интерфейс подключён к нему через HTTP-провайдеры Refine; данные хранятся в PostgreSQL, живые обновления идут по SSE.

Стек: Python 3.12, uv, FastAPI, SQLAlchemy 2 (asyncpg для входа и служебных маршрутов, psycopg для доменных правил), Alembic, Pydantic v2, PostgreSQL 16 + pgvector, pytest, ruff. Всё запускается в Docker.

## Доменные правила

Правила лежат в `app/domain`: ядро `core.py`, модули по функциям в `features/`, помощник, демо-данные. Записи и ответы — словари в форме контракта (ключи camelCase, даты — ISO-строки).

Подписи дат («Завтра, 25 октября, 10:00») зависят от пояса города, выбранного в шапке: клиент передаёт его в заголовке `X-City` (`krasnoyarsk`, `moscow`, `bryansk`).

## Хранение

Каждая коллекция правил — отдельная таблица с типизированными колонками (`app/domain/schema.py`, миграция `0002`): `events`, `participations`, `messages`, `organizations`, `venues`, `gear_loans`, `mcp_tokens` и ещё 36. Вложенные значения (место, цена, изменения «было → стало», отзывы) — JSONB. Основные связи закреплены отложенными внешними ключами. Статусы события, записи, организации, сообщения и объявления — перечисления `app/domain/statuses.py`; те же значения закреплены в таблицах ограничениями CHECK (миграция `0013`). Одна запись человека на событие, одно «в избранном» и один управляющий клуба — ограничения UNIQUE, отложенные до конца транзакции, как и внешние ключи. Совпадение миграций со схемой в коде проверяет `tests/test_migrations.py`. Таблица `users` общая с входом: правила читают и меняют поля профиля, хеш пароля остаётся у сервиса входа.

`app/domain/store.py`:

- **Коллекции по требованию.** Правило обращается к `db.events` — коллекция загружается из таблицы при первом обращении в этом запросе.
- **Запись только изменений.** После правила слой хранения сравнивает коллекции со снимком и выполняет `INSERT`/`UPDATE`/`DELETE` только для новых, изменённых и удалённых записей. Порядок записей (новые уведомления — в начале списка) хранит колонка `ord`.
- **Строгая схема.** Поле записи без колонки — ошибка `SchemaMismatchError` в разработке и тестах (`DOMAIN_STRICT=true`) и предупреждение в журнале в продакшене: ничего не теряется молча.
- **Транзакции.** Изменяющие запросы выполняются по одному: блокировка процесса и advisory-lock PostgreSQL. Номера записей (`e-sw`, `n-1kq`) идут от общего счётчика в таблице `demo_state`. Чтения идут параллельно на снимке `REPEATABLE READ`. Если правило при чтении что-то изменило (отметило ссылку-приглашение, записало поиск в журнал спроса), изменения сохраняются, если за время чтения никто ничего не записал, иначе правило выполняется заново как изменяющее.
- **Живые обновления после коммита.** `bus.publish(...)` в правиле копит события; они уходят в брокер SSE только после успешного коммита.

Объём демо-данных — около тысячи записей, коллекции загружаются за миллисекунды. При росте данных узкие места — коллекции, которые растут бесконечно (уведомления, журнал спроса): их стоит перевести на выборки по пользователю и периоду, не меняя правил.

## HTTP API

Один обработчик `/api/{путь}` (`app/api/routes/domain.py`) разбирает адрес по таблице ниже:

| Запрос | Что делает |
|---|---|
| действие из таблицы маршрутов (`POST /api/events/:id/join`, `GET /api/sports/suggest`, `PUT /api/companions/:id/metoo` …) | пользовательское действие; таблица — `provider.py` и `*_routes()` модулей |
| `GET /api/<ресурс>?filters=…&sorters=…&pagination=…` | список (`getList`): фильтры, сортировка и страницы Refine — JSON в параметрах, ответ `{ data, total }` |
| `GET /api/<ресурс>/<id>?meta={"invite":…}` | карточка (`getOne`) |
| `GET /api/_many/<ресурс>?ids=a,b` | `getMany` |
| `POST /api/<ресурс>`, `PUT /api/<ресурс>/<id>`, `DELETE /api/<ресурс>/<id>` | создание, правка, удаление |
| `POST /api/access/can` `{ resource, action, params }` | подсказка прав для интерфейса (`accessControlProvider`) |

Действие ищется раньше ресурса: `POST /api/venues/best-place` — действие, `POST /api/venues` — создание площадки. Неизвестное — `404 not_found` со стандартным текстом ошибки.

Любая ошибка сервера приходит в одном формате: `{ code, statusCode, message, errors?, …доп. поля }` (`similar` у `sport_similar`, `fallback` у `assistant_unavailable`, `conflicts` у `time_conflict`, `retryAfter` у лимитов). Коды и HTTP-статусы — перечисление `ErrorCode` в `app/core/errors.py`; правила прерываются через `fail(code, message, fields)`, служебные маршруты бросают тот же `AppError`, ответ собирает один обработчик (`app/api/errors.py`).

Документация OpenAPI — `/api/docs` (служебные маршруты; ресурсы и действия описаны в api.md).

## Вход

- **Сессия.** При входе сервер создаёт случайный токен (256 бит) и хранит в `auth_sessions` только его sha256. Токен приходит в ответе и в cookie `vmeste_session` (`HttpOnly`, `SameSite=Lax`). Интерфейс передаёт токен в заголовке `Authorization: Bearer …` и хранит его в `sessionStorage` вкладки: в двух вкладках можно держать организатора и участника. Новая вкладка берёт последний вход.
- **Демо-аккаунты.** `POST /api/auth/demo-login { userId }` — вход в один клик: на странице входа список «Демо-аккаунты всех ролей» (свёрнутый блок) берёт аккаунты из `GET /api/demo/accounts`. У демо-аккаунтов нет пароля: почту можно ввести и в обычную форму, оставив пароль пустым. Всё это работает только при `DEMO_LOGIN_ENABLED=true`; при `false` список пуст, и блока на странице нет.
- **Регистрация.** `POST /api/auth/register` — правила (имя, почта без повторов, район, интересы) и пароль не короче 8 символов; хранится хеш argon2. Ответ входа и регистрации — пользователь, токен и `identity` (форма `Identity` контракта). С `EMAIL_VERIFICATION=true` сессия начинается только после подтверждения почты — см. «Почта».
- **Права** проверяют правила на каждое действие (`fail('forbidden', …)`), прямой запрос мимо интерфейса проходит те же проверки. `POST /api/access/can` — только подсказка экрану.

## Почта

Письма двух видов: «Подтвердите почту» после регистрации и «Сброс пароля». Код — `app/mail` (отправка и шаблоны), правила — `app/services/email.py`, маршруты — `app/api/routes/auth.py`.

**Отправка.** `MAIL_ENABLED=true` — стандартный `smtplib` в отдельном потоке, таймаут 15 с, по желанию STARTTLS или SSL и вход по логину. Письмо — `multipart/alternative` (текст и HTML) с `Message-ID`, `Date` и `Auto-Submitted: auto-generated`. Письмо уходит после ответа (фоновая задача): SMTP не задерживает экран, а время ответа не выдаёт, есть ли адрес. Ошибка SMTP пишется в журнал с маской адреса (`a***@e***.ru`) и не роняет запрос — человек нажмёт «Отправить ещё раз». `MAIL_ENABLED=false` — письмо не отправляется, тема и ссылка пишутся в журнал (разработка, тесты).

**Шаблоны** (`app/mail/templates.py`): вёрстка таблицами, стили в атрибутах, ширина 600 с `max-width:100%`, скрытый прехедер, логотип `<сайт>/icon-192.png`, «пуленепробиваемая» кнопка (таблица с фоном, отступы для Outlook — на ячейке) и ссылка текстом под ней. `color-scheme: light only` и явный цвет фона у каждой ячейки: тёмная тема почтовых программ не ломает контраст. Имя экранируется. Адрес сайта для ссылок — `SITE_URL`, если пуст — из запроса (как у robots.txt).

**Хранение** (миграция `0004`):

- `email_tokens` — ссылки из писем: `purpose` `verify` (48 ч) или `reset` (1 ч), в базе только sha256 токена, `used_at` делает ссылку одноразовой. Новая ссылка того же назначения гасит прежние. Переход по ссылке блокирует строку (`FOR UPDATE`): двойной клик не пройдёт дважды.
- `email_status` — `verified_at` по пользователю. Нет строки — почта считается подтверждённой: демо-аккаунты и пользователи, зарегистрированные до включения проверки, не затронуты. Строка с `verified_at = null` появляется в транзакции регистрации при `EMAIL_VERIFICATION=true`.
- Обе таблицы ссылаются на `users` с `ON DELETE CASCADE`: сброс демо-данных удаляет зарегистрированных вместе с их ссылками.

**API:**

| Запрос | Ответ |
|---|---|
| `GET /api/auth/config` | `{ emailVerification, passwordReset }` — показывать ли «Забыли пароль?» (`passwordReset` = `MAIL_ENABLED` или `EMAIL_VERIFICATION`) |
| `POST /api/auth/register` при `EMAIL_VERIFICATION=true` | `202 { status: "verification_sent", email }`, без сессии; почта обязательна. При `false` — как раньше: `200` и сессия |
| `POST /api/auth/verify-email { token }` | `200` — ответ входа (пользователь, токен, `identity`, cookie). `400 token_invalid`, `410 token_expired`, `409 token_used` («Почта уже подтверждена…») |
| `POST /api/auth/resend-verification { email }` | всегда `200 { ok: true }`; письмо уходит, если адрес ждёт подтверждения |
| `POST /api/auth/login` | неподтверждённая почта — `403 email_not_verified` с полем `email`; проверяется после пароля, поэтому без пароля статус чужого адреса не узнать |
| `POST /api/auth/password/forgot { email }` | всегда `200 { ok: true }`; письмо уходит, если есть пользователь с паролем (демо-аккаунтам не отправляется) |
| `POST /api/auth/password/reset { token, password }` | `200` — ответ входа; новый пароль, прочие сессии закрыты, почта подтверждена. `422 validation` (`errors.password`), ошибки ссылки — как у `verify-email` |

Лимит на адрес — не чаще раза в 60 с и пяти раз в час, отдельно для подтверждения и сброса; письмо после регистрации считается первой отправкой. Превышение — `429 rate_limited { retryAfter }` и заголовок `Retry-After`. Лимит считается по адресу из запроса, поэтому ответ одинаков для существующих и несуществующих адресов. Счётчики живут в памяти процесса (бэкенд работает одним процессом).

**Переменные:**

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MAIL_ENABLED` | `false` | отправлять письма по SMTP; иначе — в журнал |
| `EMAIL_VERIFICATION` | `false` | подтверждение почты при регистрации (включать вместе с `MAIL_ENABLED`) |
| `SMTP_HOST`, `SMTP_PORT` | `mail`, `587` в compose | сервер отправки |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | пусто | вход на SMTP; пусто — без входа |
| `SMTP_STARTTLS`, `SMTP_SSL` | `false` | шифрование соединения с внешним SMTP |
| `MAIL_FROM` | `Спорт и точка <noreply@sport.up-point.tech>` | отправитель |
| `MAIL_REPLY_TO` | пусто | адрес для ответов |
| `MAIL_DOMAIN`, `MAIL_HOSTNAME` | `sport.up-point.tech` | сервис `mail`: домен отправителя и имя в приветствии SMTP |
| `MAIL_DKIM_DIR` | `./dkim` | сервис `mail`: папка с ключом `<домен>.private` (на сервере `/srv/sport-mail/dkim`) |

**Docker.** Сервис `mail` (`boky/postfix:v5.1.0-alpine`) запускается вместе с приложением, порт наружу не открыт: письма принимаются только из сети compose, сервис сам доставляет их в ящики получателей. Ключ DKIM монтируется только для чтения, селектор `mail`. Без ключа сервис стартует и отправляет письма без подписи (в журнале «No DKIM keys found»). Автогенерацию не включаем: ключ, созданный заново при пересоздании контейнера, не совпадёт с DNS. Ключ должен читаться пользователем `opendkim` в контейнере (uid 102 в образе alpine): `chown 102:103 <домен>.private`, `chmod 400`, у папки — право прохода (`chmod 711`). Иначе образ пытается сменить владельца, а на томе только для чтения это не выходит. В профиле `dev` — `mailpit` (`axllent/mailpit:v1.31.3`): `backend-dev` отправляет в него с `MAIL_ENABLED=true` и `EMAIL_VERIFICATION=true`, письма видно на http://127.0.0.1:8025, ссылки ведут на Vite (`http://localhost:5173`).

**DNS для доставки** (без них письма попадут в спам или не дойдут):

- **A и PTR.** Обратная запись IP сервера (PTR, настраивается у хостинга) указывает на `MAIL_HOSTNAME`, а A-запись этого имени — на тот же IP. Исходящий порт 25 должен быть открыт у хостинга.
- **SPF** — TXT у домена отправителя: `v=spf1 a ip4:<IP сервера> ~all`.
- **DKIM** — TXT у `mail._domainkey.<домен>`: `v=DKIM1; k=rsa; p=<открытый ключ>`, пара к ключу из `MAIL_DKIM_DIR`.
- **DMARC** — TXT у `_dmarc.<домен>`: для начала `v=DMARC1; p=none; rua=mailto:<адрес для отчётов>`, после проверки доставки — `p=quarantine`.

Проверка: отправить письмо на mail-tester.com или себе в Gmail («Показать оригинал»: SPF, DKIM и DMARC — PASS).

## SMS: код, если письмо не дошло

Запасной путь подтверждения аккаунта при `EMAIL_VERIFICATION=true`: человек вводит почту, пароль и номер, получает шестизначный код и входит. Пароль обязателен: код получает только владелец аккаунта, а не любой, кто знает адрес. Правила — `app/services/phone.py`, отправка — `app/sms`, маршруты — `app/api/routes/auth.py`.

**Отправка.** `SMS_PROVIDER=log` (по умолчанию) — текст с кодом пишется в журнал, SMS не уходят (разработка, тесты). `SMS_PROVIDER=smsaero` — SMS Aero, REST API v2: `POST https://gate.smsaero.ru/v2/sms/send`, Basic-авторизация «почта кабинета : API-ключ», тело `{number: "79…", text, sign}`, ответ `{success, data, message}`; таймаут 10 с. Текст: «Спорт и точка: код 123456. Никому его не сообщайте.» — одно SMS кириллицей (до 70 символов), имя сервиса в тексте обязательно при бесплатной подписи «SMS Aero». Для работы нужна своя подпись, одобренная в кабинете SMS Aero (`SMSAERO_SIGN`). Отказ провайдера пишется в журнал с маской номера (`+7 912 ***-**-89`), ключ в журнал не попадает; ответ — `502 sms_failed`.

**Хранение** (миграция `0005`):

- `phone_codes` — каждый запрос кода: `code_hash` = sha256(`SMS_CODE_PEPPER` + код + id), `attempts`, `expires_at` (5 минут), `used_at`, `ip`. Новый код гасит прежний. Запрос без отправки (неверная пара почта и пароль, почта уже подтверждена или письмо не уходило) тоже записывается — без пользователя и хеша: лимиты номера и IP учитывают и его, поэтому подбор пароля через этот запрос упирается в те же лимиты. Таблица — источник лимитов, они переживают перезапуск.
- `phone_status` — подтверждённый номер пользователя (`phone`, `verified_at`).
- Обе таблицы ссылаются на `users` с `ON DELETE CASCADE`.

**API:**

| Запрос | Ответ |
|---|---|
| `GET /api/auth/config` | добавлено `phoneVerification` — `EMAIL_VERIFICATION` включено и отправка SMS настроена (`log` считается настроенной) |
| `POST /api/auth/phone/send { email, password, phone }` | `200 { ok: true, resendIn: 60, expiresIn: 300 }`; SMS уходит, только если почта ждёт подтверждения и письмо ей уже отправлялось, иначе тот же ответ без SMS. `401 invalid_credentials` («Неверная почта или пароль») — пара почта и пароль не подошла, как у входа; демо-аккаунтам и аккаунтам без пароля — тоже `401`. `422 validation` (`errors.phone`: «Введите российский мобильный номер, например +7 912 345-67-89»; `errors.password`, если пароля нет), `429 rate_limited { retryAfter }` и заголовок `Retry-After`, `503 sms_unavailable` (дневной потолок или подтверждение выключено), `502 sms_failed` |
| `POST /api/auth/phone/verify { email, phone, code }` | `200` — ответ входа (пользователь, токен, `identity`, cookie), номер и почта подтверждены. `400 code_invalid { attemptsLeft }` («Код не подошёл. Осталось попыток: N»), `410 code_expired` (нет кода, просрочен, пятая ошибка) |

Номер приводится к `+7XXXXXXXXXX`: принимаются `+7 9…`, `8 9…`, `9…` с пробелами, скобками и дефисами; городские и иностранные — `422`. Лимиты: на номер — раз в 60 с, 3 в час, 5 в сутки; на пользователя — 5 в сутки; на IP — 10 в сутки; на весь сайт — `SMS_DAILY_LIMIT` отправок в сутки. Порядок проверок: формат номера → лимиты номера и IP → дневной потолок → пароль → лимит пользователя → отправка.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SMS_PROVIDER` | `log` | `log` — в журнал, `smsaero` — SMS Aero |
| `SMSAERO_EMAIL`, `SMSAERO_API_KEY` | пусто | доступ к API SMS Aero; без них `smsaero` выключает SMS (`phoneVerification: false`) |
| `SMSAERO_SIGN` | `SMS Aero` | подпись отправителя; бесплатная — только для проверки |
| `SMS_DAILY_LIMIT` | `100` | потолок SMS в сутки на весь сайт |
| `SMS_CODE_PEPPER` | случайный на процесс | секрет для хешей кодов; задать на сервере, иначе коды гаснут при перезапуске |

## Живые обновления (SSE)

`GET /api/stream` (токен вкладки — параметром `access_token`: EventSource не умеет заголовки). Каждое изменение публикует событие `live` в формате `LiveEvent` Refine в общий канал:

```
event: live
data: {"channel":"resources/events","type":"updated","payload":{"ids":["e-run-tatyshev"]},"date":"…"}
```

В событии только названия ресурсов и id, без данных: экраны перечитывают их со своими правами. Переподключение с `Last-Event-ID` дочитывает пропущенное из буфера; если буфер не помнит нужное место, приходит `resync`, и интерфейс обновляет всё. Брокер и буфер живут в памяти процесса, поэтому uvicorn работает одним процессом; для нескольких экземпляров брокер заменяется на Postgres `LISTEN/NOTIFY` или Redis с тем же интерфейсом.

## Уведомления на почту и в браузер

Источник — уведомления правил (то, что под колокольчиком). Каналы человек выбирает в настройках: почта включена по умолчанию, браузер — после подписки Web Push. Фоновая доставка (`services/delivery.py`) просыпается по живому обновлению уведомлений и раз в `DELIVERY_POLL_SECONDS`, отправляет письмо (через ту же почту, что и подтверждение: при `MAIL_ENABLED=false` — в журнал) и Web Push (`services/webpush.py`, ключи VAPID), итог пишет в `delivery_log` (миграция `0011`). Пара «уведомление, канал» уходит один раз; накопленные при первом запуске и «старые» уведомления (старше 15 минут или из будущего после сдвига дат) отмечаются без отправки. Мессенджеры сюда не входят: боты сами забирают непрочитанные уведомления ключом человека. Маршруты — `GET/PUT /api/delivery/settings`, `POST /api/delivery/push/subscribe`, `POST /api/delivery/push/unsubscribe`, `POST /api/delivery/test`.

## Проверки по времени и демо-данные

- **Фоновые проверки** раз в `DOMAIN_TICK_SECONDS` (15 с) и перед каждым изменяющим запросом: истёкшие резервы из листа ожидания, напоминания за сутки и за 2 часа, «Встреча состоялась?», неподтверждённые места команды, сроки оплаты.
- **Сиды.** Пустая база при старте получает демо-данные (`DEMO_SEED_ON_START`), даты считаются от момента загрузки. При каждой загрузке в `demo_state.settings.seedIds` записываются ключи демо-записей по коллекциям: `id`, свой ключ коллекции (`token`, `userId`) или составной ключ для таблиц без id (`provider._COMPOSITE_KEYS`, например «событие + человек» у избранного). Всё, чего нет в `seedIds`, создали люди.
- **Новая версия сидов** (`seed.SCHEMA_VERSION` не совпала с базой) вливается при старте, а не заменяет базу (`provider.merge_seed`):
  - демо-записи прошлой версии заменяются записями нового сида, исчезнувшие из сида удаляются; записи людей остаются (в коллекциях, куда правила добавляют записи в начало, — уведомления, журнал, полка — записи людей идут первыми);
  - затем по внешним ключам `schema.py` и ссылкам `{kind, id}` (организатор события, владелец вещи) повторно удаляются записи людей, которые ссылаются на исчезнувшие демо-записи, например запись на удалённое демо-событие; сколько удалено — в журнале;
  - люди не удаляются никогда: у аккаунта только обнуляется ссылка на исчезнувший район. Таблица `users` общая со входом: слой хранения обновляет только поля профиля, поэтому хеш пароля, сессии, привязки ботов и статус почты сохраняются;
  - записи о деньгах (`payments`, `paymentOps`, `paymentDues`, `orders`, `credits`, `payouts`) не заменяются, не чистятся и не дополняются новыми демо-записями. Демо-записи, на которые они ссылаются (событие, заявка, человек), сохраняются вместе со всем, на что ссылаются сами;
  - настройки помощника и ставки оплаты остаются, счётчик номеров — больший из текущего и нового (новые номера не совпадут с существующими);
  - перед слиянием снимок записей людей и записей о деньгах сохраняется в JSON в `DOMAIN_BACKUP_DIR` (`domain-<дата>-<время>-v<было>-v<стало>.json`, последние 20). В `deploy/docker-compose.yml` это том `domain-backups`, смонтированный в `/backups`.
  - В базе без `seedIds` (до этого учёта) демо-записями считаются записи с ключами из нового сида; при старте той же версии `seedIds` дописывается так же.
- **Сброс.** `POST /api/demo/reset` пересоздаёт демо-данные полностью: зарегистрированные аккаунты и записи об оплате удаляются, вкладки с ними выходят. Сброс доступен только администратору и только при `DEMO_LOGIN_ENABLED=true`: сначала вход `POST /api/auth/demo-login {"userId":"u-maria"}`, затем `curl -X POST -H "Authorization: Bearer <token>" http://localhost:8080/api/demo/reset`. На публичном сервере `DEMO_RESET_ENABLED=false`: сброс и переключатель сбоя помощника (`POST /api/demo/assistant-failure`) отвечают 404 `not_found`, как неизвестный маршрут.
- **Сдвиг дат.** Если демо-данные открыли в другой календарный день, даты демо-записей (по `seedIds`) сдвигаются на целое число дней (`DEMO_SHIFT_DATES`): «завтра» и «в субботу» снова впереди, время встреч не меняется. Встречи, записи, уведомления людей и даты их регистрации не сдвигаются: встреча, назначенная на 25-е, остаётся на 25-м. Записи о деньгах, журналы (`audit`, `mcpCalls`) и сроки действия ключей и ссылок (`expiresAt`, `revokedAt`, `lastUsedAt`) не сдвигаются никогда.

## Помощник

Разбор фраз поиска, черновики события, объявления и организации, подбор с уточнениями, объяснения «почему вам подходит», предмодерация — правила `app/domain/assistant.py` (качество разбора меряет набор `backend/tests/assistant_eval_cases.json`, прогон — `tests/test_assistant_eval.py`). Режим сбоя для демонстрации (`POST /api/demo/assistant-failure`, как и остальные `/api/demo/*` — только администратору в демо-режиме): ошибка сразу или через 6 секунд, с запасным путём (`fallback.q` для обычного текстового поиска). Каждый вызов пишется в `ai_requests` без текста запроса.

Модуль `app/ai` (адаптеры GigaChat и YandexGPT с JSON-схемой ответа, кэш, лимиты, журнал) вызывает только чат-помощник (`app/assistant/engines.py`) в режиме внешнего API, который включает администратор. Разбор фраз, черновики и подбор работают на правилах; следующий шаг — вызывать модель в `assistant.parse_search` и черновиках, оставив правила запасным путём.

## Боты

Боты Telegram и VK (`docs/product/10-bots.md`) — обычные клиенты API: ходят с личным ключом человека `stb_…` в заголовке `Authorization: Bearer`. Ключ принимается везде, где принимается вход: маршруты с `CurrentUser` (`app/api/deps.py`) и доменные действия (`services/domain.py`, тот же поиск по sha256 токена). В базе только хеш ключа, срок — 365 дней, отозванный или просроченный ключ — как недействительная сессия (401). Отметка `lastUsedAt` обновляется не чаще раза в минуту на любом запросе `/api`. Код: `api/routes/bots.py` → `services/bots.py` → `db/repositories/bots.py`, таблицы `bot_links` и `bot_codes` (миграция `0010`).

Запросы бота подписаны общим секретом `BOT_API_SECRET` в заголовке `X-Bot-Secret` (сравнение за постоянное время). Секрет не задан — привязка выключена: эндпоинты бота, `link-code` и `claim` отвечают 503 `bots_disabled`; выданные ключи продолжают работать и отключаются на сайте.

| Запрос | Кто | Ответ |
|---|---|---|
| `GET /api/bots/config` | все | `{telegram: {enabled, username}, vk: {enabled, groupId}}` |
| `POST /api/bots/link-code {platform}` | вход | `{code, url, expiresAt}`: 6 цифр, 10 минут; `url` — `t.me/<ник>?start=<код>` или `vk.me/club<группа>?ref=<код>`, без ника Telegram — `null` |
| `POST /api/bots/link {code, platform, externalId, displayName}` | секрет | `{token, user: {id, name}}` |
| `POST /api/bots/pending {platform, externalId, displayName}` | секрет | `{code, expiresAt}`; новый код гасит прежний неподтверждённый код чата |
| `POST /api/bots/claim {code}` | вход | `{platform, displayName}` |
| `GET /api/bots/pending/{code}?platform=&externalId=` | секрет | `{status: "waiting"}` или `{status: "linked", token, user}` — ключ отдаётся один раз, затем 410 |
| `GET /api/bots/links` | вход | `[{id, platform, displayName, createdAt, lastUsedAt}]` — действующие привязки |
| `DELETE /api/bots/links/{id}` | вход, своя | 204, ключ отозван сразу |
| `POST /api/bots/unlink` | ключ `stb_` | 204, отозван ключ запроса |

Ошибки: 401 `bot_secret` «Неверный секрет бота»; 400 `code_invalid` «Код не подошёл» (неверный, повторный, для другой платформы или чата); 410 `code_expired` «Код устарел. Получите новый на сайте» (у кода из бота — «…в боте»); 429 `rate_limited` с `retryAfter` и заголовком `Retry-After`.

- **Один чат — одна привязка.** Новая привязка того же чата (`platform` + `externalId`) отзывает прежнюю, даже если она была к другому аккаунту. Уникальность среди неотозванных держит частичный индекс.
- **Коды.** В базе HMAC-SHA256 кода с секретом бота: шесть цифр без секрета перебираются мгновенно. Среди действующих кодов одного вида совпадений нет. Подтверждённый на сайте код из бота живёт ещё 10 минут, чтобы бот успел забрать ключ.
- **Лимиты** (в памяти процесса): `link-code` — 5 за 10 минут на пользователя (по таблице); `link`, `pending`, `claim` — 20 в минуту; опрос `GET pending/{code}` — 60 в минуту; 10 неверных кодов за 10 минут — пауза до конца окна. Для запросов с секретом счётчик ведётся по адресу и чату (`platform:externalId`): бот ходит с одного адреса, и ошибки одного человека не блокируют остальных. Для `claim` — по адресу.
- **Лимит помощника.** `POST /api/assistant/chat` с верным `X-Bot-Secret` и заголовком `X-Bot-Chat` (до 100 символов) считает 12 вопросов в минуту на чат, а не на адрес бота. Без секрета `X-Bot-Chat` не учитывается.
- **Сброс демо-данных** удаляет пользователей, их привязки и коды удаляются каскадно. Демо-аккаунты привязывать можно.

| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_*` | пусто | магазин ЮKassa, чеки, выплаты, проверка адресов уведомлений — `docs/features/payments-yookassa-setup.md` |

## Запуск в Docker

```bash
# Приложение: база, бэкенд, nginx со сборкой фронтенда — http://localhost:8080
COMPOSE_BAKE=false docker compose -f deploy/docker-compose.yml up -d --build --wait

# Разработка: бэкенд перезапускается при правке, Vite с горячей заменой — http://localhost:5173
COMPOSE_BAKE=false docker compose -f deploy/docker-compose.yml --profile dev up -d --build db backend-dev frontend-dev

# Тесты и линтер бэкенда
COMPOSE_BAKE=false docker compose -f deploy/docker-compose.yml --profile test run --rm backend-test
```

| Сервис | Что делает |
|---|---|
| `db` | PostgreSQL 16 + pgvector, данные в томе `db-data`, порт только на `127.0.0.1:5433` |
| `backend` | миграции Alembic при старте, uvicorn одним процессом, загрузка демо-данных в пустую базу и слияние новой версии сидов, healthcheck `/api/health` |
| `web` | сборка фронтенда (`npm run build`, провайдеры сервера), nginx: статика, прокси `/api` (SSE без буферизации) и `/mcp`, SPA-маршруты |
| `mail` | Postfix для писем подтверждения и сброса пароля, только внутри сети compose, DKIM — см. «Почта» |
| `vk-bot` | VK-бот (`bots/`, `deploy/bot.Dockerfile`) — клиент API; без `VK_GROUP_TOKEN` пишет предупреждение в журнал и ждёт. Telegram-бот в compose не входит, его запускают отдельно (`scripts/run-telegram-bot.ps1`) |
| `backend-dev`, `frontend-dev` | профиль `dev`: исходники смонтированы томами |
| `mailpit` | профиль `dev`: ловушка писем, веб-интерфейс http://127.0.0.1:8025 |
| `backend-test` | профиль `test`: `ruff check`, `ruff format --check`, `pytest` на базе `vmeste_test` |

`COMPOSE_BAKE=false` нужен, когда путь к репозиторию содержит кириллицу. Для HTTPS перед `web` ставится внешний прокси, и задаётся `COOKIE_SECURE=true`.

Новая миграция — в контейнере разработки: `alembic revision --autogenerate -m "…"`, затем ручная проверка файла.

## Тесты и сценарии

- **pytest** (`tests/`): только самое важное, прогон занимает пару минут: шесть базовых сценариев кейса по HTTP (`test_scenarios.py`), выключатели ИИ (`test_ai_switches.py`), ответ модели в чате, оплата, вход и сессии, удаление аккаунта, ошибки, слой хранения, демо-данные, совпадение миграций со схемой.
- **Оценка помощника**: 65 фраз `backend/tests/assistant_eval_cases.json` прогоняет `tests/test_assistant_eval.py`.
- **Сценарии запросов** (`scripts/scenarios/`, см. README там): сценарий `.json` прогоняется в контейнере `backend-test` (сервер в процессе, отдельная база), коды ответов сравниваются с прошлым прогоном, 5xx — ошибка. Запуск: `scripts/scenarios/run.sh <сценарий.json> [--expect коды.json] [--out коды.json]`.
- **Браузер** (`scripts/e2e/`): Chromium в Docker против поднятого стека — вход, лента, запись кнопкой, уведомление организатору и живое обновление без перезагрузки.

## Ограничения

- **Один процесс бэкенда**: брокер SSE, буфер повторной доставки, защита от повторного учёта поиска, лимит сообщений и лимит отправки писем живут в памяти (после перезапуска лимит писем начинается заново).
- Коллекция правил загружается целиком при первом обращении в запросе — достаточно для демонстрационного объёма; для роста данных см. «Хранение».
- Нет ограничения частоты попыток входа по паролю; при публичном запуске добавить лимит по IP и почте и выключить демо-вход (`DEMO_LOGIN_ENABLED=false`).
- Адаптеры GigaChat и YandexGPT используются только чатом в режиме внешнего API, к правилам помощника не подключены и с настоящим ключом не проверялись.
