# Контракт HTTP API

Контракт HTTP API сервера (`backend/app/domain`, устройство — `docs/architecture/backend.md`). Интерфейс (`frontend/src/api`) подключает его как `dataProvider` Refine поверх `/api/<ресурс>`: списки, карточки и правки — ресурсами, остальное — действиями вида `METHOD /api/<ресурс>/:id/<действие>`.

По HTTP: список — `GET /api/<ресурс>` (фильтры, сортировка и страницы Refine JSON-строками в `filters`, `sorters`, `pagination`, ответ `{ data, total }`), карточка — `GET /api/<ресурс>/<id>`, создание, правка, удаление — `POST`, `PUT`, `DELETE`, действия — адреса из таблиц ниже с префиксом `/api`.

Типы ответов — `frontend/src/types/api.ts`, тела запросов — `frontend/src/types/inputs.ts`, сущности — `frontend/src/types/domain.ts`.
Хуки для экранов — `frontend/src/lib/api.ts` (адреса действий в `API`, `useAction`, `useMetoo`, `useAppealEvent`, `useReadNotifications`, `isSportSimilar`, `assistantFallbackQuery`, `newIdempotencyKey`).
Сервер отвечает без искусственных задержек. Режим таймаута помощника — 6 с и ошибка.

## Общие правила

- Все ответы зависят от того, кто смотрит (`actor`). Гость получает публичные поля; приватные сведения события (`privateInfo`) видят подтверждённые участники, организатор и админ.
- **Служебные поля только админу.** В событии `aiFlag` / `aiReason` приходят как `'none'` / `''`, `moderation.by` — пустой строкой, `createdBy` — пустой строкой (организатору — заполнен), `moderation.appeal` — только организатору и админу, `changes[].acknowledgedBy` — только сам смотрящий (организатору и админу — все). В сообщении `aiFlag` / `aiReason` (там бывает цитата из скрытого текста) — только админу. В объявлении «Ищу компанию» `point` для всех, кроме автора, — центр района, а не адрес автора.
- Ошибка: `{ code, statusCode, message, errors?, ... }`. `message` — готовый русский текст для человека, `errors` — ошибки полей формы `{ поле: текст }`. Дополнительные поля: `similar` у `sport_similar`, `fallback` у `assistant_unavailable`.
- Права проверяются в домене на каждое действие. Прямая ссылка или вызов API в обход интерфейса не обходят правила.
- **Свежие данные и откат.** Каждое изменяющее обращение (`create`, `update`, `deleteOne`, `custom` кроме GET) выполняется в одной транзакции БД: при ошибке недоделанное изменение откатывается. Номера новых записей идут от общего счётчика, параллельные запросы не затирают друг друга.
- **Проверки до изменений.** Создание события сначала проверяет организацию, поля, объявление «Ищу компанию» и направление, и только потом что-то записывает.
- **Повторы безопасны.** Повтор того же решения (`decide`, `leave`, `cancel`, `moderate`, `organizations/decide`, скрыть/вернуть сообщение, «Я тоже», закрыть объявление, удалить своё) возвращает текущее состояние, а не 409. Создание события и сообщения принимает `idempotencyKey`: повтор с тем же ключом возвращает уже созданное.
- **Даты в текстах.** Уведомления, системные сообщения и журнал хранят даты как ISO (`{{date:ISO}}`) и подписывают их при чтении («Завтра, 25 октября, 10:00»). В `changes` время хранится ISO и приходит подписанным.
- Каждое изменение публикует событие в канал `resources/<ресурс>` (`type`: `created` / `updated` / `deleted`, `payload.ids`). Подписка на все ресурсы — канал `resources/*`.

## Ресурсы (getList / getOne / create / update / deleteOne)

Фильтры `getList` передаются как фильтры Refine `{ field, operator: 'eq', value }`. Поля, которые ресурс не обработал сам, применяются к полям ответа (`eq`, `ne`, `in`, `contains`, `gte`, `lte`). Сортировка — по любому полю ответа, пагинация `currentPage` / `pageSize` или `mode: 'off'`.

### events → `EventView` (список), `EventDetails` (одно)
| Операция | Кто | Что делает |
|---|---|---|
| getList | все | фильтры: `scope` (`feed` — опубликованные и идущие, по умолчанию; `participating`; `organizing`; `org` + `orgId`; `user` + `organizerUserId`; `admin` — все, только админ), `q`, `sportId` / `sportIds`, `when` (`today` / `tomorrow` / `weekend` / `week` / `date` + `date`), `dayPart` (`morning` / `day` / `evening`), `level`, `beginners`, `free`, `priceMax`, `joinMode`, `near` + `radiusKm` (от точки пользователя или `point`), `districtId`, `forYou` (подборка с «почему вам подходит»), `aiFlagged`, `status`, `ids` |
| getOne | все | карточка; `manage` (заявки, участники, лист ожидания, отказы) — только организатору и админу. Удалённое событие для остальных — ошибка `event_deleted` (текст различает «удалено модератором» и «организатор удалил») |
| create | пользователь; представитель допущенной организации с `orgId` | `EventInput`. Публикуется сразу. Обязательны название, направление, начало, длительность, место, режим записи и **стоимость** (`price`; без неё 422 «Укажите стоимость…»). По умолчанию: `level: 'any'`, `cancelPolicy: anytime`, пустой «Первый шаг», `discussion: 'everyone'`. Координаты: из запроса, иначе по известному месту, иначе центр района, иначе центр города. Своё направление `newSportName` — см. «Направления без дублей». `repeatWeeklyUntil` создаёт серию до 12 встреч. `companionId` — «Собрать встречу» из объявления. `idempotencyKey` — защита от двойного нажатия |
| update | организатор | `EventPatch`, **белый список полей**: `title`, `description`, `startsAt`, `durationMin`, `place`, `level`, `beginnersWelcome`, `firstStep`, `price`, `paymentNote`, `cancelPolicy`, `joinMode`, `capacity`, `minParticipants`, `privateInfo`, `discussion`, `extra`, `coverUrl`. Всё остальное (статус, организатор, `createdBy`, пометки помощника, модерация) молча отбрасывается. Можно править предстоящее событие и **снятое модератором** (пока оно не прошло). Время, место, длительность, лимит, цена, режим записи попадают в `changes` («было → стало»); у предстоящего — участникам уведомление и системное сообщение, у снятого — без уведомлений (изменения увидят после возврата). Новый адрес без координат пересчитывает точку. Лимит нельзя сделать меньше числа участников и меньше порога. Рост лимита поднимает лист ожидания. Смена «по заявке → свободная» принимает ждущие заявки, пока есть места, остальных ставит в лист ожидания. Правка названия или описания заново проходит предмодерацию: помощник может поднять пометку, снимает её только админ |
| deleteOne | организатор | только без активных участников, иначе `has_participants` (событие с людьми — только отменить). Удалённое организатором админ не восстанавливает |

Дополнительные поля `EventView`:
- `coverUrl` — обложка: HTTPS-адрес или уменьшенный JPEG/PNG/WebP data URL, до 160 000 символов. `photos` — альбом «Как это было», до четырёх элементов `{ id, url, caption }`.
- `gathered` — порог сбора набран (`true` / `false`), `null` — порога нет; `thresholdDeadline` — к какому времени его нужно набрать (за 24 часа до начала), `null` — порога нет.
- `can.edit` — можно открыть правку; `can.appeal` — можно попросить вернуть снятое событие. Поля необязательные в типе для совместимости, сервер заполняет их всегда.

`PUT /events/:id/photos`, только организатору начавшейся или прошедшей встречи: `{ photos: [{ url, caption }] }`. Полностью заменяет альбом, пустой массив убирает фотографии. Те же ограничения на источник изображения, подписи до 180 символов, максимум четыре фото. Ошибки: `auth_required`, `forbidden`, `bad_state`, `validation`. Возвращает обновлённый `EventDetails`, публикует изменение ресурса `events`.

### participations → `ParticipantView`
getList: `eventId` (организатор или админ) или свои записи. Статусы: `confirmed`, `pending`, `waitlist`, `rejected`, `cancelled`, `event_removed` (событие снято модератором; при возврате восстанавливается прежний статус).

`scope: 'organizer_pending'` → `OrganizerPendingView[]` — стопка «Разобрать по одной» в кабинете: все заявки `pending` по событиям, где пользователь организатор (сам, представитель организации или соуправляющий), пока по ним можно принять решение (идёт или предстоит; отменённые, снятые, удалённые и прошедшие не попадают). Остальные фильтры при этом не действуют. Порядок: по `event.startsAt`, при равном начале — по id события, внутри события — по `createdAt` заявки. Запрашивать с `pagination: { mode: 'off' }`. Гость — `auth_required`, человек без своих событий и админ без своих событий — пустой список. Элемент — `ParticipantView` плюс:
- `event`: `{ id, title, startsAt, capacity, confirmedCount, seatsLeft, joinMode, sport: { id, name }, coverUrl }`; `confirmedCount` — занятые места в составе (дети считаются), `seatsLeft` — как `counts.spotsLeft` (с придержанными местами), `null` без лимита;
- `seats` — сколько мест займёт «Принять»: заявитель, его дети и ждущие участники команды (та же формула, что в `decide`);
- `attended` — прошедших встреч у заявителя, то же число, что `UserView.facts.attended`;
- `firstVisit` — человек отметил «Я здесь впервые» на этой встрече.

Новая заявка, отзыв, решение, отмена и правка события публикуют ресурс `participations`, поэтому `useList` с живыми обновлениями перечитывает стопку сам.

### messages → `MessageView`
| Операция | Кто | Что делает |
|---|---|---|
| getList | все | `eventId` — обсуждение события по времени. Публичное обсуждение доступно для чтения всем; у встречи по приглашению проверяется доступ к самой встрече. Настройка `discussion: 'participants'` ограничивает отправку сообщений. `scope: 'flagged' / 'hidden' / 'all'` — очереди админа |
| create | вошедший | `{ eventId, text, replyTo?, idempotencyKey? }`. Под публичной встречей со свободной записью вопрос может задать любой вошедший пользователь, включая незаписавшегося; `discussion` принудительно равен `everyone`, в том числе для старых записей. Для остальных встреч разрешено ограничение участниками. Неактивное событие — только чтение. Не больше 5 сообщений за 30 секунд. Помощник ставит `aiFlag` и `aiReason`, ничего не скрывая. Ответ организатора помечается (`author.isOrganizer`, от имени организации — `asOrgId`) |
| deleteOne | автор | сообщение помечается удалённым, в ленте — «Сообщение удалено автором» |

Скрытое сообщение отдаётся с `text: null`, админ видит текст и причину. `hiddenBy`: `admin` / `organizer` — скрытое админом организатор вернуть не может.

### organizations → `OrganizationView`
| Операция | Кто | Что делает |
|---|---|---|
| getList | все | `scope`: `public` (только допущенные, по умолчанию), `mine`, `admin`; `status`, `q`, `aiFlagged` |
| getOne | все | недопущенная организация видна только представителю и админу, остальным — `not_found` «Страница организации пока недоступна» |
| create | пользователь | `OrganizationInput` + `submit` (сразу на проверку) или черновик. Помощник ставит пометку `suspicious` с причиной (предоплата на карту, нет адреса, «документы после оплаты», нереальная скидка, нет контактов, продажа вместо занятий) |
| update | представитель | правка; при `submit` отклонённая или возвращённая заявка снова уходит на проверку. Заявку на проверке и заблокированную менять нельзя |

### companions → `CompanionView`
getList: открытые объявления, отсортированы по совпадению с профилем (`matchReasons`); фильтры `sportId`, `districtId`, `q` (с основами слов), `status`, `mine`. create: `CompanionInput` (+ `confirmNew` для своего направления). Точка объявления — выбранная автором или центр района, домашний адрес не сохраняется. deleteOne — **устарело**, то же, что `POST /companions/:id/close`.

## Направления без дублей

Новое имя (`newSportName`, `sports.create`) нормализуется (регистр, ё, лишние пробелы) и сверяется с названиями и синонимами каталога с учётом окончаний («йогу» → «Йога»), опечаток («валейбол») и общих основ («Скандинавка» ~ «Скандинавская ходьба», «Фиджитал-футбол» ~ «Футбол»).
- Совпало с названием или синонимом — берётся существующее направление.
- Похоже — `409 sport_similar`, в ответе `similar: SportSuggestion[]` и текст «Похожее направление уже есть: … Выберите его или подтвердите, что „…“ — новое». Повтор запроса с `confirmNew: true` создаёт новое.
- Иначе создаётся пользовательское направление (`kind: 'custom'`), оно сразу работает в поиске и фильтрах, админ видит его в журнале и может перевести в каталог или объединить.

## Порог сбора

У события может быть `minParticipants` — «состоится, если наберётся N». После записи, отмены, решения по заявке, подъёма из листа ожидания, «Собрать встречу» и правки порога сервер сверяет число подтверждённых участников:
- набралось — всем подтверждённым и организатору уведомление `threshold_reached` «Встреча состоится» и системное сообщение в обсуждении;
- снова стало меньше — организатору `threshold_lost` «Участников меньше порога».

Платформа сама встречу не отменяет: решает организатор. Во view — `gathered` и `thresholdDeadline`.

## Действия (custom)

| Метод и адрес | Тело | Кто | Результат |
|---|---|---|---|
| POST `/events/:id/join` | `{ note? }` | вошедший пользователь | `EventDetails`. Свободная запись → `confirmed`, по заявке → `pending`, мест нет → `waitlist` (человеку уведомление с номером в очереди). Приглашённый «Позвать» на событие по заявке сразу становится участником. Повтор не создаёт вторую запись |
| POST `/events/:id/leave` | — | участник | `EventDetails` + `lateCancel` (отмена платной записи после срока бесплатной отмены). Освободившееся место получает первый из листа ожидания. Повтор возвращает текущее состояние. После начала — `event_started` |
| POST `/events/:id/cancel` | `{ reason? }` | организатор | событие `cancelled`, участникам уведомление (при платном — про полный возврат) |
| POST `/events/:id/ack-changes` | — | участник с активной записью | «Я в курсе» для всех изменений; без записи — `no_participation` |
| POST `/events/:id/appeal` | `{ comment? }` | организатор снятого события | «Попросить вернуть»: `moderation.appeal = { at, comment }`, админам уведомление `appeal`, запись в журнал `event.appeal`. Только пока событие не прошло |
| POST `/events/:id/moderate` | `{ action: 'remove' / 'restore' / 'delete', ruleId, comment? }` | админ | для `remove` и `delete` **пункт правил обязателен** (`reason_required`). Снятие переводит записи в `event_removed`, уведомляет организатора и участников, пишет в журнал. Возврат восстанавливает записи и снимает пометку помощника. Удалённое самим организатором вернуть нельзя (`event_inactive`) |
| POST `/events/:id/dismiss-flag` | — | админ | «Оставить»: снять пометку помощника, запись в журнал `event.keep` |
| POST `/events/:id/invite` | `{ userId, companionId? }` | организатор | приглашение и уведомление. Нельзя позвать себя и админа; с `companionId` — только автора или откликнувшегося |
| POST `/participations/:id/decide` | `{ decision: 'accept' / 'reject', reason? }` | только организатор события (не админ) | принять при свободных местах, отклонить с необязательной причиной. Когда места кончились, остальные ждущие заявки уходят в лист ожидания; после отказа лист ожидания продвигается |
| POST `/messages/:id/react` | `{ key: 'thanks' / 'agree' / 'going' }` | вошедший | переключить реакцию |
| POST `/messages/:id/moderate` | `{ action: 'hide' / 'restore' / 'keep', reason?, ruleId? }` | админ или организатор события | скрыть с причиной (автору уведомление), вернуть, оставить. `keep` и снятие пометки помощника — только админ (журнал `message.keep`); организатор не возвращает скрытое админом |
| POST `/organizations/:id/submit` | поля заявки | представитель | на проверку из черновика, отказа или доработки |
| POST `/organizations/:id/decide` | `{ decision: 'approve' / 'reject' / 'return', reason? }` | админ | для отказа и доработки причина обязательна (видна организации) |
| PUT `/companions/:id/metoo` | — | вошедший, не автор | «Я тоже»: поставить отклик. Повтор ничего не меняет |

| POST `/companions/:id/close` | — | автор или админ | закрыть объявление |
| POST `/sports/:id/promote` | `{ icon?, categoryIds?, popular? }` | админ | пользовательское направление в каталог |
| POST `/sports/:id/merge` | `{ into }` | админ | объединить: события, объявления, организации и интересы переносятся, имя становится синонимом |

## Демо-данные и даты

Данные хранятся в PostgreSQL. Пустая база при старте получает демо-данные. Если версия сидов в коде новее, чем в базе, при старте новая версия вливается в базу: демо-записи заменяются, записи людей и записи о деньгах остаются (подробно — «Проверки по времени и демо-данные» в `backend.md`). Пересоздать данные целиком можно только сбросом `POST /demo/reset`. При `DEMO_SHIFT_DATES=true`, когда сменился календарный день, все даты (события, записи, уведомления, журнал, в том числе внутри текстов) сдвигаются на целое число дней, время встреч не меняется, изменения людей сохраняются. `GET /demo/state` отдаёт `datesShiftedAt` и `datesShiftedDays` — для плашки «Данные обновлены».

## Вход

`authProvider.login({ userId })` — вход в один клик по демо-аккаунту; `login({ email })` — по почте из демо-данных (пароль не проверяется). `register(RegisterInput)` создаёт пользователя; пароль обязателен, не короче 8 символов. Сессия хранится отдельно в каждой вкладке: в двух вкладках можно держать организатора и участника.

Роль для интерфейса (`Identity.role`): `admin`; `org` — пользователь, у которого есть организация (в любом статусе, чтобы отклонённая могла исправить заявку); `user`; гость — `guest`.

## Журнал (`audit`)
Пишутся решения админа (организации, снятие, возврат, удаление, «оставить» по пометке помощника — `event.keep` и `message.keep`, скрытие и возврат сообщений, направления) и действия организаторов, важные для разбора: решения по заявкам, отмена и перенос событий, просьба вернуть снятое событие (`event.appeal`), новые пользовательские направления. Поля: кто, действие, объект, пункт правил, причина, когда.

## В7, С4, С6, С9, С10: состав, место из листа ожидания, план Б, личный календарь, серия

Модули (`backend/app/domain/features`): `composition.py`, `waitlist_offer.py`, `plan_b.py`, `calendar.py`, `series.py`; общий интерфейс к доменному слою — `participation_host.py`, демо-данные — `seed/participation.py`. Правила проверяют тесты бэкенда.

### Новые поля
- `SportEvent.composition?: 'mixed' | 'women' | 'men'` (нет поля — смешанный). Принимается в `EventInput` и `EventPatch`; смена состава попадает в `changes` («Состав: было … стало …»), уже записавшихся не выписывает.
- `User.gender?: 'female' | 'male' | null` — меняется через `PUT /users/:id` (`ProfilePatch.gender`), отдаётся только в `GET /me` (`Identity.gender`), в `UserView` не попадает.
- `Participation.offer?: { until, at } | null` — придержанное место из листа ожидания; `Participation.leftBecause?: 'reschedule' | null`.
- `MyParticipation.offerUntil` — до какого времени держится место (только у предстоящего события); `MyParticipation.leftBecause`.
- `EventCounts.spotsLeft` считает придержанные места занятыми.
- `SearchFilters.composition` — фильтр ленты (`{ field: 'composition', operator: 'eq', value }`, в адресе ленты `?who=women`).
- `Database.reminders?: string[]` — ключи отправленных напоминаний; `settings.shortReserve?: boolean`.

### Правила
- **Состав.** На встречу «только женщины» / «только мужчины» записывается (и подаёт заявку) только человек с подходящим полом в профиле. Без пола — `gender_required` (409), с другим полом — `composition_mismatch` (403); в `can.joinReason` — готовый текст. Проверка в `canJoin`, поэтому действует и для серии, и для плана Б, и для любых других путей записи.
- **Место из листа ожидания.** Освободилось место при лимите мест и свободной записи (или у приглашённого) — первому в очереди без резерва ставится `offer` на 3 часа (`shortReserve` — 2 минуты) и приходит `waitlist_offer`. Придержанное место нельзя занять записью или принятием заявки (`full`). Без лимита мест человек сразу в составе, при записи по заявке заявка по-прежнему уходит организатору. Отказ, выход из очереди или истёкший срок передают место следующему. Истёкший резерв: запись становится `cancelled`, человеку — `offer_expired`. Сроки проверяются при каждом обращении к API, отдельного таймера нет.
- **Пересечения.** `POST /events/:id/join` с `checkConflicts: true` отвечает 409 `time_conflict` со списком `conflicts: TimeConflict[]`, если в это время у человека подтверждённая запись, заявка, придержанное место или своя встреча. Повтор без флага — «Всё равно записаться». Без флага поведение записи прежнее.
- **Напоминания.** Подтверждённым участникам — за сутки и за 2 часа (`reminder`), каждое один раз; после переноса — заново. Кто записался уже внутри окна, напоминание этого окна не получает.
- **План Б.** Похожие встречи: то же направление (с учётом объединённых), предстоящие, ±2 дня от исходного времени, есть места, человеку можно записаться; ближе к нему, потом по времени; до трёх. Встречи, куда человек записался уже после срыва, остаются в списке со статусом. Уведомление об отмене ведёт на `/events/:id#plan-b`.
- **Серия.** Записаться на все предстоящие встречи серии: каждая проходит обычную запись (места, режим, состав); что не удалось — с причиной. Отмена одной встречи — обычный `leave`.

## Подборка дня: три подходящие встречи раз в день

Правила — `backend/app/domain/features/digest.py`, письма — `backend/app/services/digest_mail.py` и `backend/app/mail/digest.py`. Описание — `docs/features/daily-digest.md`.

### Данные
- `Database.digestPrefs?: DigestPrefs[]` — настройки человека: `on`, `hour` (8, 12 или 18 по поясу его города), `email`, `lastDay` (местная дата последней попытки, не ISO, поэтому сдвиг демо-дат её не трогает), `token` (ключ ссылки «Отписаться»). Нет записи — подборка выключена. У демо-аккаунтов включена на 8:00, на сайте; сегодняшняя считается отправленной.
- `Database.digests?: Digest[]` — отправленные подборки: `items: { eventId, reasons }[]`, `createdAt`, `day`, `trigger` (`schedule` / `manual`), `mail` (`queued` → `sending` → `sent` / `failed` / `skipped`; `null` — без письма), `intro`.

### Правила
- Встречи берутся из «Для вас» человека (`listEvents(actor, { scope: 'feed', forYou: true })`), затем, если не хватило до трёх, — ближайшие открытые по интересам (причина «Вы отметили в интересах: …»). Только предстоящие в ближайшие 7 дней, в городе человека, с `can.join` и свободными местами, которых не было в его прошлых подборках.
- Пустую подборку не присылаем: `send-now` отвечает `{ sent: false, message }`, плановая просто пропускает день.
- Плановая (`digestTick`, проверка при каждом обращении, как напоминания): включена, наступил выбранный час по поясу города, сегодня попытки ещё не было. Не чаще раза в день; «Прислать сейчас» тоже считается подборкой этого дня.
- Письмо — только если включено «На почту» и почта настоящая (не `@vmeste.demo`) и подтверждена (на сервере — таблица `email_status`). Правило ставит письмо в очередь, отправляет асинхронный слой сервера.

## D-16: стоп-лист организатора и «Убрать из участников»

Правила: `backend/app/domain/features/stop_list.py`, сценарии запросов — `scripts/scenarios/flows-stoplist.json`. Описание — `docs/features/stop-list.md`.

### Данные
- Коллекция `stopList` (`StopEntry[]`, таблица `stop_entries`): одна запись на пару «чей список (`ownerKind` + `ownerId`) — кто в нём (`userId`)». `user:<id>` — личный список организатора, `org:<id>` — общий список клуба. Состояние: `lifted`, если снято администратором; иначе `expired`, если `until` ≤ сейчас; иначе `active`. Действует только `active`, срок проверяется при каждом обращении, без таймера.
- Статус записи `removed` и поле `Participation.removedReason` (колонка `participations.removed_reason`). Активные статусы (`ACTIVE_PARTICIPATION`) его не включают.
- Новые поля ответов: `EventPermissions.joinCode` (код любой причины отказа в записи, пусто, если можно), `MyParticipation.removedReason` (только при `removed`), `ParticipantView.stopListed` (человек в действующем стоп-листе организатора этой встречи). В `manage.declined` попадает и `removed`.

### Правила
- Ключ владельца списка во встрече — `${organizer.kind}:${organizer.id}`. Встречи от своего имени и встречи клуба — разные списки.
- Править список: `user:<id>` — только сам организатор, `org:<id>` — владелец и соуправляющие. Администратор только читает (заметки ему приходят пустыми) и снимает запрет. Иначе `forbidden` «Стоп-лист ведёт организатор».
- Нельзя добавить (`cannot_block`, текст и в `StopPreview.blockedReason`): себя; владельца и соуправляющих клуба; администратора; того, у кого нет ни одной записи на встречи этого организатора и ни одного сообщения в их обсуждениях.
- Причины: `no_show`, `rude`, `rules`, `other` (текст 5–200 знаков, иначе `validation` с полем `reasonText`). Заметка — до 300 знаков. Срок: `forever`, `month` (+30 дней), `three_months` (+90 дней).
- Повтор обновляет причину, заметку, срок, `addedBy`, `updatedAt` и сбрасывает снятие; `createdAt` прежний (`stop.update` в журнале).
- `cancelUpcoming: true` — записи `confirmed` / `pending` / `waitlist` на встречи организатора, которые ещё идут или впереди, становятся `removed` с подписью причины; места освобождаются как при уходе, лист ожидания продвигается. Отдельных `removed_from_event` нет — всё в одном `stop_listed`.
- Проверка при записи (`can_join`, сразу после `rejected_before`, раньше приглашения по ссылке): своя запись `removed` → `removed_before`; действующая запись в стоп-листе → `organizer_blocked` «Организатор ограничил вашу запись на свои встречи. Причина: … До 20 ноября.»
- Пути записи: обычная запись и заявка, лист ожидания, продвижение очереди и предложение места (человек пропускается; «Иду» на место, придержанное раньше, — `organizer_blocked`), серия (встреча пропускается с причиной), команда («Кто-то из команды не может записаться на встречи этого организатора», имя не раскрывается), ссылка-приглашение (стоп-лист сильнее), «Позвать» и «Пригласить своих» (`stop_listed`), «Собрать встречу» из «Ищу компанию» (человек не переносится), «Собраться снова» и предложение клуба по спросу (не зовём), MCP и чат-бот — через общие правила.
- Обсуждение: человек из стоп-листа читает, но не пишет («Организатор ограничил ваше участие в своих встречах, писать сюда нельзя»).
- Подбор: «Для вас», подборка дня, похожие встречи плана Б и подбор помощника не предлагают встречи организатора, который не пускает человека.
- Убрать из участников: только организатор встречи, встреча идёт или впереди (иначе `event_inactive`), статус `confirmed` / `pending` / `waitlist` (иначе `bad_state`; повтор для `removed` возвращает текущее). С `stop` — сначала проверки стоп-листа (при ошибке запись не меняется), затем то же, что `POST /stop-list`.
- Истёкшие и снятые записи видны в списке ещё 30 дней (истёкшие — от `until`, снятые — от `liftedAt`), из данных не удаляются. Сигнал администратору: человек в стоп-листах у 3+ разных организаторов, записи не сняты и добавлены или обновлены за последние 30 дней.

### Уведомления
| Событие | Тип | Получатели |
|---|---|---|
| добавили в стоп-лист (в том числе повторно) | `stop_listed` | сам человек: организатор, срок, причина-категория, сколько записей отменено; ссылка на страницу организатора (`/orgs/:id`, `/profile/:id`) |
| убрали из участников | `removed_from_event` | сам человек, с причиной; ссылка на встречу |
| организатор убрал из стоп-листа (запись действовала) | `stop_lifted` | сам человек |
| администратор снял запрет | `stop_lifted` | команда организатора (с причиной; ссылка `/me/stop-list` или кабинет `/org/:id`) и сам человек |

Журнал: `stop.add`, `stop.update`, `stop.remove`, `stop.lift` (объект — `user`, в причине — категория, без заметки), `participation.remove`.
